# ZUI 库优化审计清单

## 发现分类

每项发现同时标注“状态”和“严重度”。

状态：

- `confirmed-defect`：源码控制流、可复现行为、类型/构建结果或明确契约冲突已经证实；
- `risk`：存在可信风险，但还缺少运行时或契约证据；
- `gap`：缺少公开文档、示例、语言覆盖、无障碍或规范要求；
- `improvement`：不改变行为的可维护性、类型或结构改进。

严重度：

- `P0`：阻断构建、发布或核心使用路径；
- `P1`：公开 API 错误、数据损坏、明显运行时故障、严重生命周期或无障碍问题；
- `P2`：重要边界错误、文档误导、缺少主要示例/i18n 覆盖或显著维护风险；
- `P3`：低风险一致性、可读性或次要覆盖改善。

不要仅按文件风格或代码行数定级。每项记录目标库、类别、证据路径/行、影响范围、建议、负责技能和验证方式。

## 审计维度

### 1. Package 与公共契约

- `zui.type`、`displayName`、`contributes` 是否与真实产出一致；
- `main`、`browser`、`module`、`exports`、`files` 的目标是否存在；
- 运行时依赖和仅文档/调试依赖是否正确分类；
- `src/main.ts`、局部 `index.ts` 与实际公共 API 是否一致；
- 是否暴露了不稳定深层路径，或遗漏已有公共类型/类/方法；
- 跨库导入是否使用 `@zui/*`，是否意外依赖 `exts/`。

### 2. 组件和 helper 代码质量

- 类型是否准确，是否以 `any`、断言或重复类型掩盖契约问题；
- 默认值、受控/非受控状态、事件参数/顺序、方法返回值是否一致；
- 重复初始化、更新、销毁、重入、异步竞态和错误恢复是否可靠；
- listener、timer、observer、portal、缓存和 DOM 引用是否清理；
- store/helper 的副作用、序列化、浏览器全局和失败回退是否明确；
- 是否复用 core/Preact/Cash 与现有组件，而非重复基础设施；
- 热路径、列表渲染和缓存是否存在有证据的性能问题；
- 语义标签、键盘、焦点、ARIA、reduced motion 和 disabled 状态是否完整。

先复现或通过源码路径证实行为缺陷。只看到“可能”时标为 `risk`，在计划中加入验证，不直接改代码。

### 3. 公开 API 文档

同时检查源码 JSDoc 和官网正式文档：

- 公开组件、函数、类、构造器、options/props、方法、成员、事件和类型是否有准确说明；
- 默认值、错误、异步、生命周期、返回值和兼容性是否明确；
- 文档是否只描述真实导出，示例是否使用真实 API；
- `lib/<name>/docs/lib/<category>/index.md` 第一屏是否有可运行基础示例；
- HTML/CSS、Preact、vanilla、自动创建/toggle 等已承诺消费方式是否覆盖；
- CSS 类、变量、无障碍和限制是否与源码一致。

正式文档只写库内源文件，不编辑生成目录 `docs/_`。

### 4. 开发调试页

- `README.md` 是否覆盖默认、主要变体、交互和边界，而不只是静态外观；
- 示例是否真实运行，ID/selector 是否唯一，依赖和资源是否正确；
- `dev.ts` 是否把 DOM 重建逻辑放在 `onPageUpdate`；
- 全局监听、实例、timer 和 observer 是否重复或泄漏；
- 是否能观察事件、方法、更新、destroy、错误和语言切换；
- HMR 后是否仍保持正确行为。

“更多示例”应增加可验证状态和行为覆盖，不机械复制相似 DOM。

### 5. 国际化

- 用户可见字符串是否仍硬编码；
- `zh_cn`、`zh_tw`、`en` 的键、嵌套和占位符是否一致；
- 私有静态映射或全局命名空间选择是否正确；
- 语言文件是否从真实入口加载；
- 全局语言、实例 `lang`、实例 `i18n` 覆盖和缺失键回退是否实际生效；
- 动态语言变化是否需要重渲染或状态失效；
- 文档/调试页是否覆盖三语言与 fallback。

### 6. 规范与样式

- 新代码是否遵循当前 `AGENTS.md`、ESLint、Preact 和路径别名规则；
- 已有库的合理局部结构是否被保留；
- CSS 根类、变量、Tailwind `-` 前缀、主题和 dark mode 是否一致；
- 是否存在无关迁移、格式化或对公共契约的隐式破坏。

## 范围策略

### 单库

完成深度审计后，形成一份覆盖选中领域的集成计划。若只做只读审计，直接输出完整发现与修复顺序。

### 多库

先画出依赖和共享问题：

- 共享 helper/core 缺陷单独成项，先于消费者；
- 相同表象但不同根因分别处理；
- 公共基础修改与各库适配放在同一可验收批次；
- 每库保留独立验证结果，不用一次组合构建掩盖局部失败。

### 全库或大范围

1. 用盘点脚本建立当前清单，保留 WIP/notReady 标记；
2. 浅审全部库，按包角色、依赖、严重度和领域分组；
3. 先处理 P0/P1 和共享基础，再处理 P2/P3；
4. 将工作拆成能独立验证的批次，通常优先保持每批约 3–8 个相关库，而不是固定数量；
5. 每批深审后提交决策完整计划，完成并验证后再进入下一批。

不要在一份计划中罗列尚未读源码的“预计修复”。

## 基线与验收

确认前通过源码、package 解析、`git diff` 和不会写 cache/生成物的静态检查记录基线。不要为了基线运行会刷新 `build/`、`dist/`、`docs/_` 或仓库缓存的命令；把这些命令及预期副作用写进计划。确认并实施后按影响选择：

- 目标文件 ESLint 与 TypeScript；
- `pnpm build -- --lib=<name> --noMinify`；
- helper 的临时可执行边界检查；
- `pnpm docs:prepare -- --copy --build=no` 和必要的 `pnpm docs:build`；
- `pnpm dev` + `/<lib-name>/` 的首次加载、HMR 和主要交互；
- 多库批次的组合构建与依赖方回归。

区分本次引入失败和仓库基线失败。无法运行的检查说明原因，不宣称通过。

## 计划记录格式

为每项批准内容记录：

| 字段 | 内容 |
| --- | --- |
| Library | 精确目标库 |
| Finding | 状态、严重度和证据 |
| Change | 具体优化与非目标 |
| Compatibility | 公开 API、DOM、CSS、事件和依赖影响 |
| Owner skill | `zui-lib`、`zui-component`、`zui-helper`、`zui-doc`、`zui-dev` 或 `zui-i18n` |
| Files | 允许修改的边界 |
| Acceptance | 可观察验收场景 |
| Validation | 命令和人工检查 |

实施中新增项必须先进入记录；若超出当前批准范围，移到后续批次或重新确认。
