# ZUI 技能协作工作流

## 规则优先级

遇到冲突时按以下顺序执行：

1. 用户当前明确要求；
2. 仓库根目录及目标路径适用的 `AGENTS.md`；
3. 当前构建脚本、类型定义和运行时基础设施；
4. 与目标最相近且成熟的现有库；
5. 本技能的参考规范。

本规范总结当前仓库惯例，但不是源码的替代品。发现规范与实现基础设施不一致时，以可验证的仓库事实为准，并在交付中指出差异。

## 探索原则

- 从请求涉及的路径定位包含 `AGENTS.md`、`pnpm-workspace.yaml` 和 `lib/` 的仓库根，读取目标适用的 `AGENTS.md`，检查 Git 状态并保留用户已有改动。
- 本任务首次需要某项规范或上下文时读取；内容仍在上下文且文件未变化时直接复用，技能切换不重新执行整套准备。目标、路径、元数据或相关实现变化时只刷新受影响部分。
- 先检查当前请求、已确认决定和目标现状。能够合理沿用既有约定时采用并说明；只有仍有无法可靠消除、会实质改变目标、公开契约、实现架构或交付边界的歧义时才询问。不要询问可从源码、包元数据或已有文档发现的事实。
- 先阅读目标位置及判断本次变更所需的上下文。涉及新架构、公开契约或现有模式无法解释的问题时，再检查相关基础设施和相似成熟实现；参考数量由证据需要决定，不为局部文案、样式或已知行为修复强制阅读整个库。
- 盘点脚本可用于定位目标和筛选候选；脚本信号不能证明 API 或架构正确，决策所需事实仍从相关源码、类型、入口或实际行为核实。纯 `exts/` 注册核对目标契约与接入结果。
- 新内容采用统一规范；优化已有库时保留合理的局部目录和 API 风格，不顺带迁移无关代码。遇到重叠修改时先理解，不覆盖或回退无关内容。
- 跨库导入使用 `@zui/<name>`，不要通过相对路径穿越 `lib/` 边界。
- 不依赖 `exts/` 中特定扩展库，除非用户明确把它纳入目标。

## 复用已有能力

新增组件、helper 或为已有库增加能力前，先按所需行为检索现有实现；本任务已有且仍有效的检索结果直接复用。优先使用目标库已有能力和其他库的公开组件、函数、类型或基础设施，能通过配置、组合或少量适配满足需求时，不复制实现或另造同类工具。

```sh
node <zui-standards技能目录>/scripts/inspect-zui-lib.mjs --root <ZUI_ROOT> --search '搜索 search debounce' --json
node <zui-standards技能目录>/scripts/inspect-zui-lib.mjs --root <ZUI_ROOT> --lib core --search 'debounce 防抖' --json
```

`--search` 按空白分词，以大小写不敏感的字面子串匹配任一词，检索包元数据、源码路径与内容、README/dev.md 和正式文档。使用与任务相关的中英文功能词或符号名；结果给出真实包名、位置、状态和命中证据。主仓库开发只检索内置库，不因本机存在 `exts/` 就引入扩展依赖；扩展开发按扩展版工作流同时检索宿主和扩展项目。

- 命中只是候选，源码中出现某个名称不代表它已公开。读取候选库的公共入口、类型和必要用例，核实导入方式、行为、生命周期、兼容性与依赖方向，避免循环依赖和私有深层导入。
- 未命中时换用相关术语或符号名，必要时在相关目录用 `rg` 定向补查；结果截断时缩小关键词或用 `--lib` 定位。不要把一次无结果视为没有可复用能力。
- 在本次设计中简述采用的已有 API 和证据路径；仍需新增实现时，说明现有能力的具体缺口或不适用原因。只实现缺口，不为未来复用提前抽象，也不为了复用擅自修改其他库或扩大公共 API。

## 实施方式

用户要求开发、优化或修复且需求明确时，完成必要调查和规划后直接实施，不等待用户对计划另行确认。用户只要求分析、审计、评审或制定计划时，保持只读；用户明确要求先确认再实施时遵循该要求。

| 技能 | 独立调用 |
| --- | --- |
| `zui-standards` | 只读分析；实施任务查询后继续相应技能 |
| `zui-component` | 明确设计后直接实施 |
| `zui-helper` | 明确设计后直接实施 |
| `zui-doc` | 需求明确后在文档边界内直接实施 |
| `zui-dev` | 需求明确后在调试页边界内直接实施 |
| `zui-i18n` | 需求明确后在 i18n 边界内直接实施 |
| `zui-lib` | 汇总集成计划后直接实施 |
| `zui-wrap-lib` | 汇总资源与封装计划后直接实施 |
| `zui-optimize` | 审计保持只读；优化完成调查和规划后按批次连续实施 |
| `zui-commit` | 用户直接调用即授权提交；审查与必要检查通过后直接提交，明确只读请求除外 |

多个技能组合时共享任务范围、已有决定和计划，不因技能切换或批次推进增加确认步骤。

整库质量审计、多库或跨领域优化使用 `zui-optimize`；单独的文档、调试页或 i18n 需求优先使用对应专用技能，不要仅因请求含“优化”“完善”就进入 optimize。

## 任务范围

按用户请求和已有明确决定确定实施范围，计划中按需记录：

- 精确目标库与新建/已有库状态；
- 包角色、公开 API、消费方式、兼容性承诺，以及资源/依赖和跨库影响（若有）；
- 允许修改的领域与文件边界；
- 组件/helper/i18n/文档/调试页中的纳入项和排除项；
- 验收场景、验证方式及假设。

任务范围内的实现调整和新发现可更新计划后继续处理。需要超出用户请求、改变用户明确指定的文件边界，或仍存在会实质改变交付且无法合理判断的歧义时，只澄清受影响部分，继续不受影响的工作和验证。最终说明已完成、被阻断和未验证事项；存在必要未完事项时不宣称任务全部完成。

实施始终服从当前协作模式和更高层仍生效的 Plan Mode 或只读约束。

## 计划质量

计划完整是指本次决策明确、可以直接实施，不要求每次重述整库设计。局部修复说明问题依据、目标行为、修改边界和验收方法；未变化的架构、API、依赖和兼容契约引用现状即可。

新建或改变对应设计时，展开领域清单中的相关项：包角色与架构、公开消费方式和 API、状态与副作用、生命周期、入口及依赖、文档/dev/i18n、验证方式和剩余假设。不适用项无需填充；不能省略影响任务范围的关键决定，也不能把这些决定推迟到编码阶段。

## 实施与验证

- 只实施用户请求范围内的工作，遵循仓库代码风格。
- 实施任务包括完成修改、运行必要检查、修复本次修改引入且位于授权范围内的问题，并复跑受影响检查。不要把首次实现或可自行修复的失败当作完成。范围外问题单独报告；需要澄清任务范围、遇到无法解决的阻断或必要验收未完成时，明确剩余工作并继续不受影响部分。
- 所有领域技能和参考文件中的验证清单都按本次变更涉及的行为选用：新增或改变相应能力时覆盖其清单，局部修订只检查受影响行为和相关回归。用户明确指定的验收项目仍须完成，不将完整清单作为每次任务的固定成本。
- 优先使用现有目标 lint、类型和相关 unit/DOM 测试；只有涉及分发、资源、样式或构建契约时才增加必要的目标构建，涉及交互、焦点或 HMR 时增加对应浏览器检查。单库构建通常使用 `pnpm build -- --lib=<name> --noMinify`；具体命令和覆盖范围以当前脚本为准。
- 同一快照已有的有效验证结果可以复用；仅在变更、失败或新风险需要时补充验证。区分本次引入、基线和环境失败，不把未运行写成通过。
- 不手工修改生成产物来代替修改源文件。常规验证沿用当前请求或计划已有的授权；运行前识别生成物、缓存和中间目录，优先使用包含目标改动的隔离副本或临时输出，并核对实际隔离范围。不得覆盖用户已有产物；需要超出已授权写入范围时，列明具体路径和副作用并取得许可。
- 开发服务的启动、复用、重启和清理统一遵循 `AGENTS.md` 的“开发服务管理”，保留服务归属和临时验证/持续预览用途。
- 开发或评审任务不自动提交；用户直接调用 `zui-commit` 即授权按其范围规则提交，不自动推送或发布。最终报告修改范围、验证结果和未验证风险。
