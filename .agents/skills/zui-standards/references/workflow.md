# ZUI 技能协作工作流

## 规则优先级

遇到冲突时按以下顺序执行：

1. 用户当前明确要求；
2. 仓库根目录及目标路径适用的 `AGENTS.md`；
3. 当前构建脚本、类型定义和运行时基础设施；
4. 与目标最相近且成熟的现有库；
5. 本技能的参考规范。

本规范总结当前仓库惯例，但不是源码的替代品。发现规范与实现基础设施不一致时，以可验证的仓库事实为准，并在交付中指出差异。

## 探索原则

- 先检查当前请求、已确认决定和目标现状。能够合理沿用既有约定时采用并说明；只有仍有无法可靠消除、会实质改变目标、公开契约、实现架构或交付边界的歧义时才询问。不要询问可从源码、包元数据或已有文档发现的事实。
- 设计、实现或审查库源码时至少检查两个相似实现。优先匹配包角色、实现架构、消费方式和关键依赖，不要只按名称相似选择；纯 `exts/` 注册只核对目标契约与接入结果。
- 盘点脚本只用于筛选；最终决策必须阅读入口、类型、实现、样式、文档和调试页。
- 检查 `git status` 并保留用户已有改动。遇到重叠修改时先理解，不覆盖或回退无关内容。
- 新内容采用统一规范；优化已有库时保留合理的局部目录和 API 风格，不顺带迁移无关代码。
- 跨库导入使用 `@zui/<name>`，不要通过相对路径穿越 `lib/` 边界。
- 不依赖 `exts/` 中特定扩展库，除非用户明确把它纳入目标。

## 确认门禁

| 技能 | 独立调用 |
| --- | --- |
| `zui-standards` | 只读分析 |
| `zui-component` | 先给出设计计划，明确确认后实施 |
| `zui-helper` | 先给出设计计划，明确确认后实施 |
| `zui-doc` | 需求明确后在文档边界内直接实施 |
| `zui-dev` | 需求明确后在调试页边界内直接实施 |
| `zui-i18n` | 需求明确后在 i18n 边界内直接实施 |
| `zui-lib` | 汇总一份集成计划，只确认一次 |
| `zui-wrap-lib` | 汇总 UMD 资源、库骨架与组件/helper 的集成计划，只确认一次 |
| `zui-optimize` | 审计保持只读；优化先统一规划，大范围按批次确认 |

单纯回答问题、修改细节或选择批次不构成批准；同一回复同时明确表达实施授权，且最终范围无实质歧义时，按该范围执行。需要计划确认的任务仍须用户明确同意，不能从讨论或计划标题推断授权。

多个轻量技能组合时统一直接实施。组合包含 component 或 helper 时，共用一份计划和一次确认。本任务中已有的明确批准，只要仍完整覆盖计划承诺的目标、包角色、公开 API、兼容性、资源/依赖、跨库影响、文件边界和验收场景，就在后续步骤及技能切换中继续有效，包括 `zui-wrap-lib` 的协调计划；不因协调技能名称或步骤变化而重复确认。

整库质量审计、多库或跨领域优化使用 `zui-optimize`；单独的文档、调试页或 i18n 需求优先使用对应专用技能，不要仅因请求含“优化”“完善”就进入 optimize。显式调用或任务确需 optimize 编排时，即使批次只含轻量领域，也保留其统一计划及后续未知批次的确认门禁。

## 计划范围与批准状态

批准前标记为“拟实施范围”，收到明确批准后才记为“已批准范围”，并关联实际批准内容。计划中明确记录：

- 精确目标库与新建/已有库状态；
- 包角色、公开 API、消费方式、兼容性承诺，以及资源/依赖和跨库影响（若有）；
- 允许修改的领域与文件边界；
- 组件/helper/i18n/文档/调试页中的纳入项和排除项；
- 验收场景、验证方式及假设。

需要超出批准范围时，暂停该部分及依赖它的写操作，向当前协调流程提交具体增量计划并取得明确批准；继续当前已批准范围内不受影响的工作和验证，以及必要的只读调查。小型内部实现调整可在不改变承诺时继续，但不得自行扩展精确文件边界。最终分别说明已完成、待批准、被阻断和未验证事项；存在必要未完事项时不宣称任务全部完成。

确认门禁始终服从当前协作模式。用户批准计划不能覆盖更高层仍生效的 Plan Mode 或只读约束。

## 计划质量

component、helper 或完整库计划至少回答：

- 类型判断及依据；
- 目标、非目标与验收场景；
- 公开 API 和消费方式；
- 状态、数据流、副作用与生命周期；
- 文件、入口、依赖和元数据；
- 文档、调试页和 i18n 是否纳入；
- 验证命令、边界场景和剩余假设。

计划应达到确认后可直接实施的程度，不把关键设计决定推迟到编码阶段。

## 实施与验证

- 只实施用户要求或已批准范围。
- 遵循 4 空格缩进、分号、1tbs 和紧凑对象大括号等仓库 ESLint 规则。
- 验证与风险相称：优先针对性 lint/类型检查、目标库构建、文档同步和调试页交互。
- 单库构建通常使用 `pnpm build -- --lib=<name> --noMinify`；根据任务补充更窄的静态检查。
- 不手工修改生成产物来代替修改源文件。常规验证沿用当前请求或计划已有的授权；运行前识别生成物、缓存和中间目录，优先使用包含目标改动的隔离副本或临时输出，并核对实际隔离范围。不得覆盖用户已有产物；需要超出已授权写入范围时，列明具体路径和副作用并取得许可。
- 开发服务的启动、复用、重启和清理统一遵循 `AGENTS.md` 的“开发服务管理”，保留服务归属和临时验证/持续预览用途。
- 仓库没有统一单元测试套件时，通过类型检查、可执行脚本、调试页和正式示例覆盖验收场景。
- 不自动提交、推送或发布。最终报告修改范围、验证结果和未验证风险。
