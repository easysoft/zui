# ZUI 外部扩展库协同开发规范

## 概念边界

把另一个本地项目中的一个或一组 ZUI 库注册到当前仓库的 `exts/`，使开发服务器、构建脚本和文档工具能够共同发现它们。注册使用符号链接，不复制外部源码。

不要把这套机制与浏览器运行时加载第三方 JS/CSS 混淆：

- 本文的 `exts/` 面向本地 ZUI 库的联合开发与构建；
- `LibLoader<T>` 面向组件首次使用时加载 UMD/IIFE 等外部资源，遵循 [external-library.md](external-library.md)。

`exts/` 被 gitignore，且被 `pnpm-workspace.yaml` 排除。把注册视为当前机器的开发环境配置，不假定它会被提交、随仓库共享或在 CI 中存在。

## 注册前检查

1. 定位当前 ZUI 仓库根目录和外部目标的真实路径，确认目标存在。
2. 判断目标是单库还是库集合：
   - 单库根目录包含带有效 `zui` 元数据的 `package.json`；
   - 库集合根目录的直接子目录分别包含各自的 `package.json`。
3. 按 [library.md](library.md) 核对每个库的 `name`、入口、`zui.type`、`zui.contributes` 与依赖；发现无效 `zui.type` 时库发现会失败。
4. 为本次注册选择稳定且唯一的扩展组名。默认使用目标目录名；同一集合后续调试、构建和文档命令都用这个组名。
5. 检查 `exts/<组名>` 与 `exts/libs.json` 是否已有同名记录。目标一致时复用；目标不一致时不要覆盖或删除，先明确替换范围。
6. 外部目标若属于另一个仓库，先读取其适用的 `AGENTS.md` 并检查其 Git 状态。注册只授权接入调试，不自动授权修改外部源码，也不要通过符号链接绕过文件权限。

## 添加到当前仓库

在 ZUI 仓库根目录运行：

```sh
pnpm extend-lib <外部路径> --name=<扩展组名>
```

省略 `--name` 时使用目标目录名。命令会：

1. 把相对路径解析为绝对路径；
2. 创建 `exts/<扩展组名>` 符号链接；
3. 更新 `exts/libs.json` 中“扩展组名 → 外部绝对路径”的映射；
4. 当目标根目录本身不是一个 ZUI 库时，把映射记为 `<外部路径>/*`，按直接子目录发现一组库。

优先使用命令维护符号链接和映射，不手工制造两者不一致的状态。命令不会安装依赖，也不会修改 `pnpm-workspace.yaml`、根 `package.json` 或锁文件。外部库需要额外依赖时，先根据外部仓库自身约定确定安装位置，不为消除解析错误而直接把依赖塞入 ZUI 根项目。

当前没有对应的取消注册命令。只有用户明确要求移除或替换时，才处理精确的 `exts/<扩展组名>` 链接和对应映射；绝不能删除符号链接指向的外部源码目录。

## 库发现与解析

`scripts/libs/query.ts` 的 `getLibs()` 是统一发现入口：

- `buildIn` 发现当前仓库的 `lib/*`；
- `exts` 读取 `exts/libs.json` 并发现所有已注册扩展组；
- 指定扩展组名时只扫描 `exts/<扩展组名>`；
- 扩展库会获得 `zui.sourceType = 'exts'` 与对应的 `zui.extsName`；
- Vite 会为扩展包的真实包名及已声明的 `zui.replace` 注册路径别名；
- 扩展库自己的 `tailwind.cjs` 或 `tailwind.js` 会进入联合开发配置。

库集合只扫描一层直接子目录。不要依赖更深的隐式递归，也不要让不同扩展库使用冲突的 `zui.name`；库映射合并时同名项会互相覆盖。

## 联合调试

注册完成后重新启动开发服务器。默认加载全部内置库和全部已注册扩展库：

```sh
pnpm dev:exts
```

缩小发现范围时使用扩展组名，而不是猜测包的短名称：

```sh
pnpm dev:exts -- --lib=buildIn,<扩展组名>
pnpm dev:exts -- --lib=<扩展组名>
```

从开发页左侧导航进入目标库；扩展项会显示扩展组标签。开发服务器优先加载库根目录的 `dev.ts`，缺失时回退到 `src/main.ts`；页面内容优先使用 `dev.md`，再回退到 `README.md`。修改符号链接指向的源码后应由 Vite/HMR 直接更新。

新增注册、增删库目录或修改 `package.json` 后，停止并重启开发服务器。若元数据仍陈旧，检查生成缓存 `.cache/zui-libs.json`；只有确认是缓存问题时才清理这个精确文件。

## 构建与文档

构建时分别指定“发现哪些来源”和“选择哪些库”。默认 `pnpm build` 只发现内置库：

```sh
# 内置库 + 所有已注册扩展库
pnpm build -- --exts=buildIn,exts --lib='zui*exts' --noMinify

# 内置库 + 一个扩展组
pnpm build -- --exts=buildIn,<扩展组名> --lib='zui*<扩展组名>' --noMinify

# 已发现范围中的单个扩展库
pnpm build -- --exts=buildIn,<扩展组名> --lib='<准确的 zui.name>' --noMinify
```

引号用于防止 shell 展开 `*`。`--exts` 只控制候选库来源，`--lib` 控制最终构建集合；缺少任一侧都可能导致扩展库未被发现或未被选中。

需要把已注册扩展库的正式文档和资源一起同步、监听或构建时使用：

```sh
pnpm docs:dev:exts
pnpm docs:build:exts
```

文档开发是持续进程，完成验证后主动结束。不要编辑生成目录 `docs/_`。

## 边界与验收

- 内置 `lib/*` 不得无意硬依赖本地 `exts/`；只有用户明确把扩展库及相应构建环境纳入交付时才允许跨边界协作。
- 跨 ZUI 库导入继续使用公开包名，不通过相对路径穿越仓库或符号链接边界。
- 不把本机绝对路径、`exts/libs.json` 或符号链接当成可发布配置；需要 CI 或团队复现时，另行设计显式的检出与注册步骤。
- 不因联合调试顺手修改外部仓库的无关文件、依赖策略或提交历史。

至少验证：

1. `exts/<扩展组名>` 指向预期目标，`exts/libs.json` 的单库/集合映射正确；
2. `pnpm dev:exts` 导航能识别目标库并显示扩展组标签；
3. 目标库的 `dev.ts`、页面内容、样式、跨库导入及 HMR 正常；
4. 若交付包含构建或文档，运行对应的扩展构建/文档命令；
5. 当前仓库和外部仓库的既有未提交改动均未被覆盖，注册没有引入应提交的根项目依赖或锁文件变化。
