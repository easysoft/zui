# ZUI 扩展库外部资源按需加载规范

## 边界

当第三方 JS/CSS 不编入 ZUI bundle，而要在浏览器运行时从 `$.libRoot` 或指定地址首次加载时，使用当前 `ZUI_ROOT` 的 `LibLoader<T>`。

- 随 bundle 静态打包的依赖继续使用普通 import 和扩展项目依赖策略。
- 组件不要直接调用底层 `$.getLib` / `$.registerLib`、手写资源标签或维护第二份模块缓存。
- `dev.ts` 可以用同一注册名覆盖开发资源地址。
- 只封装已经可由目标浏览器直接加载、形状明确的资源；格式转换或重新打包是另一项任务，不由此规范隐式完成。

## 以当前宿主为事实来源

按本次涉及的加载决策核实当前宿主 `LibLoader` 和底层加载函数；需要参考时优先检查相近扩展 wrapper，再按证据需要补充宿主实现。复用仍适用的发现，不硬编码宿主路径、API 或缓存行为。

## Loader 所有权与资源路径

- 同一扩展包对同一外部模块共享一个模块级 `LibLoader<T>`，通常保持在私有 helper 中。
- 使用全局唯一注册名并显式提供 `check`；多个扩展包共享能力时优先依赖拥有该 loader 的公开包。
- loader 的生产注册必须从真实 package 入口可达，导入组件本身不应立即下载资源。
- 本地托管资源放入 `TARGET_LIB_ROOT/public/`，生产 `src` 使用构建后相对于 `$.libRoot` 的路径；根据真实 `PUBLIC_PATH` 核对最终位置。
- 联合开发覆盖路径使用宿主验证出的扩展 URL，当前常见形式是 `/exts/<EXTS_NAME>/<LIB_FOLDER>/public/<asset>`，不要写死扩展组。
- 多个 JS/CSS、前置依赖与 module 类型使用宿主加载 options 表达，不在生命周期中手写顺序。

## 类型与公开 API

优先使用与运行时全局形状一致的第三方声明，并保持 runtime import 为 type-only。若声明不可靠，只为 facade 使用面手写窄类型。若公开类型引用第三方包，按 `DEPENDENCY_POLICY` 确保消费者可解析。

loader 默认保持私有。只有用户确实需要预加载、显式重试或同步读取已加载模块时，才设计公开方法；不要机械暴露第三方全部 API。

## 生命周期、失败与重试

- 在真正需要能力时调用 `load()`；await 后同时检查模块结果和当前实例是否仍存活。
- 明确加载前、加载失败后、重试中和销毁后公开方法的行为。
- 使用当前宿主 loader 的错误缓存与显式重试 API，不用循环初始化制造隐式重试。
- 多实例共享模块加载，但各自持有和清理自身第三方实例。
- `destroy()` 清理第三方实例、listener、DOM、worker、timer 和其他副作用；防止资源返回后的迟到初始化。

## 计划与验证

计划与批准遵循 [共享工作流](workflow.md)；本次涉及的加载决策包括资源与全局、注册与 `check`、生产/dev 路径、类型及 facade、失败重试、销毁与依赖。未变化部分引用现状。

按共享工作流选择本次所需验证。新增封装或改变对应行为时，检查相关的按需加载、预载复用、并发、失败重试、销毁竞态、更新清理、类型或资源路径；涉及宿主契约时再补充所需联合验证。验证不得修改宿主依赖或锁文件。
